# TASKS-80: Generate release notes from CHANGES.md with tag-pinned links

Status: active

## Description

Improve the GitHub Release notes generated by the release workflow so each release automatically includes its corresponding section from `CHANGES.md` along with clickable `blob/$tag/` links to `CHANGES.md` and `docs/adrs/0002-provenance-based-releases.md`, backed by on-`main` CI checks to catch changelog formatting problems and relative links before an immutable tag is pushed.

## Requirements

### Release note extraction and rendering

- Factor release-note extraction and rendering into a reusable bash helper script (e.g. `bin/render-release-notes`) using only standard shell tools already present in the `publish` job (no Go toolchain or new GitHub Actions dependencies), so it can be shared by `bin/publish-release`, `bin/check-release-tag`, CI, and local previews.
- Extract the section matching the release tag (`vMAJOR.MINOR.PATCH`) from `CHANGES.md`: match a level-2 heading `^## <tag>([[:space:]]|$)` through the next `^## ` or `^# ` heading (ignoring headings inside fenced code blocks), trim leading and trailing blank lines, and fail if the section is missing, empty, or duplicated.
- Construct links dynamically from `${GITHUB_SERVER_URL:-https://github.com}/$GITHUB_REPOSITORY/blob/$tag/...` (preserving compatibility with staging rehearsals and tests):
  - Link to `CHANGES.md` at `.../blob/$tag/CHANGES.md`.
  - Link to ADR-0002 at `.../blob/$tag/docs/adrs/0002-provenance-based-releases.md`.
- Render multi-line GitHub-flavored Markdown containing:
  - The extracted changes section for `$tag`, followed by a link to `CHANGES.md` for the full changelog.
  - The installation, runtime, and verification section retaining the ADR-0002 requirements (shared `libgit2 1.9.x` runtime requirement, Ubuntu 26.04 `libgit2-1.9` / macOS 15 Homebrew `libgit2` details, `BUILD-INFO.txt` reference, and archive verification instructions linking to ADR-0002).

### Release workflow and publication

- Update the `publish` job in `.github/workflows/release.yml` so `sparse-checkout` includes `CHANGES.md` and any new helper script alongside `bin/publish-release`, remaining pinned to `needs.verify-tag.outputs.commit` with no changes to `.github/workflows/actions.lock`.
- Update `bin/publish-release` to render the release notes into a temporary file (cleaned up via `trap`) and pass `--notes-file` to `gh release create` instead of the hardcoded `--notes` string. Resolve `CHANGES.md` relative to the script/repository root before `cd "$assets_dir"`, with an overridable path (e.g. env var or argument) for isolated testing.
- Update `bin/check-release-tag` to verify that the pushed tag has a valid, non-empty section in `CHANGES.md` (failing fast in `verify-tag` before the 4-target build matrix runs).

### CI checks on `main`

- Add a CI check wired into both `bin/ci` and `.github/workflows/ci.yml` (since `ci.yml` invokes each check script individually) that validates `CHANGES.md`:
  - Every `## vX.Y.Z` version heading in `CHANGES.md` is unique and extracts a non-empty body using the exact same extractor used at release time.
  - `CHANGES.md` contains no relative Markdown links: reject inline links `[text](target)`, image links `![alt](target)`, `#anchor` links, and reference-style link definitions `^[label]: target` whose destination does not start with `https://`, `http://`, or `mailto:`. Ignore fenced code blocks and inline backtick code spans to avoid false positives.

### Tests

- Update `bin/test-publish-release` to test `--notes-file` output using synthetic `CHANGES.md` fixtures and assert on the rendered Markdown (extracted changes, `blob/$tag/CHANGES.md` and `blob/$tag/docs/adrs/0002-provenance-based-releases.md` links, runtime/verification notes, and rejection of missing/empty/duplicate sections).
- Update `bin/test-release-tag` to include a `CHANGES.md` fixture in its temporary test repository and verify rejection when the tagged version is missing from `CHANGES.md`.
- Add unit tests for the release-notes renderer and `CHANGES.md` validator covering normal sections, multi-paragraph and fenced-code sections, missing/empty/duplicate sections, relative inline/image/anchor/reference links, valid absolute links, links inside code spans/fenced code blocks, and validation against the repository's real `CHANGES.md`.
- Run `bin/ci` and confirm all checks pass.
